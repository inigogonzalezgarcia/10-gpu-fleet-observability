# Design decisions

## 1. Alert on what needs a different action, not on every metric

Each alert maps to one action and one receiver: drain, quarantine, cordon, check the exporter, look for a common cause, or tell the owners. If two conditions lead to the same action they share an alert (`GPUHardwareXID` covers six XIDs). The `action` label is meant for automation, such as the remediation controller in repo 09.

## 2. Hardware alerts fire immediately, everything else waits

XID 79, uncorrectable ECC and row remapping failures have no `for:`: one occurrence is enough, and waiting only means more jobs land on a broken GPU. Temperature, NVLink errors and idle GPUs are trends, so they wait (2 to 30 minutes) to avoid paging on a spike.

## 3. Capacity counts missing GPUs, not only broken ones

`fleet:gpus_healthy:ratio` divides by the GPUs expected from exporter targets, not the GPUs currently reporting. Otherwise a node whose exporter dies disappears from both numerator and denominator and the fleet looks healthier than before. The unit test "Fleet capacity counts missing exporters" covers this case.

## 4. Inhibit the idle alert on broken GPUs

A GPU that fell off the bus reports 0% utilisation, which is exactly what an idle notebook looks like. Without the inhibition the owning team would get a "you're wasting a GPU" message for a hardware failure. The end-to-end test posts both and checks only the right one reaches the team.

## 5. Recording rules for everything a dashboard or alert reads twice

Dashboards, the capacity alert and the report read the same numbers. Recording them once keeps the definitions in one file and makes dashboards cheap on a large fleet. The report command deliberately uses raw metrics instead, so it works against any Prometheus that scrapes dcgm-exporter.

## 6. Test the rules, not only the config

`promtool check` only proves the YAML parses. `promtool test rules` feeds synthetic series and asserts which alerts fire and when, with their exact labels and annotations. It runs in seconds in CI, so timing changes (`for:` durations, windows) are caught before they reach Prometheus.

## 7. Generate the dashboard

The Grafana JSON is generated by `tools/gen_dashboard.py`; CI fails if the committed JSON differs. Hand-edited dashboard JSON drifts and is hard to review. The end-to-end test also runs every panel query against Prometheus, so a renamed recording rule breaks the build instead of leaving an empty panel.

## 8. A simulator, not GPUs

Same reasoning as repo 09: no GPU in CI and no budget for one. The simulator keeps dcgm-exporter's metric names and labels, including pod attribution, so the rules and dashboards are written against the real schema. What it does not reproduce: the exact field set of a given exporter version, and how messy real failures are.

## 9. Lab intervals

Scrape and evaluation every 5 seconds and Alertmanager's `group_wait` of 5 seconds keep the end-to-end run under 10 minutes. The production values are in comments next to each setting; dcgm-exporter itself collects every 30 seconds by default, so scraping faster than that in production adds load without adding information.
