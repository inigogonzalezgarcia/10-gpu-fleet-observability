# GPU Fleet Observability

Metrics, alerts, routing and a dashboard for a fleet of GPU nodes, built on the metrics NVIDIA's dcgm-exporter publishes. Every alert has a runbook, unit tests with `promtool`, and an end-to-end test that breaks a simulated fleet and checks who gets told.

**dcgm-exporter metrics → recording rules → alerts with runbooks → Alertmanager routing and inhibition → Grafana + fleet report**

![ci](https://github.com/inigogonzalezgarcia/10-gpu-fleet-observability/actions/workflows/ci.yml/badge.svg)

> A learning-in-public lab about running GPU clusters. I don't have production GPU fleet experience; this is how I am learning what to watch. There is no GPU here: a simulator serves dcgm-exporter's metric names and labels for 4 nodes × 8 GPUs. It is the observability half of [09 GPU Node Remediation](https://github.com/inigogonzalezgarcia/09-gpu-node-remediation), which acts on the same signals.

## What it answers

| Question | Where |
|---|---|
| How many GPUs do we have, how many are assigned, how busy are they? | `fleet:*` recording rules, dashboard top row, report |
| Which GPUs must leave service, and why? | `gpu:unhealthy`, hardware alerts with an `action` label (drain / quarantine / cordon) |
| Are we blind anywhere? | `GPUExporterDown`; capacity counts missing GPUs, not only broken ones |
| Is something fleet-wide going on? | `GPUFleetHealthyCapacityLow` (under 90% healthy and reporting) |
| Who is holding GPUs without using them? | `gpu:allocated_idle:30m`, `GPUAllocatedButIdle` routed to the owning team |
| Which team uses what? | GPU-hours and idle GPU-hours per namespace in `fleetreport` |

## Alerts

| Alert | Fires | Severity → receiver |
|---|---|---|
| GPUFellOffBus | XID 79, immediately | critical → pager, `action=drain` |
| GPUHardwareXID | XID 48, 63, 74, 95, 119, 120 | critical → pager, `action=drain` |
| GPUUncorrectableECC | double-bit ECC errors | critical → pager, `action=drain` |
| GPUMemoryUnrepairable | row remapping failure, XID 64/92 | critical → pager, `action=quarantine` |
| GPUTemperatureCritical / High | ≥ 90°C for 2 min / ≥ 85°C for 5 min | critical / warning |
| NVLinkErrorsIncreasing | > 1 CRC error/s for 10 min | warning → ticket |
| GPUExporterDown | no telemetry for 1 min | critical → pager |
| GPUFleetHealthyCapacityLow | < 90% of expected GPUs healthy for 5 min | critical → pager |
| GPUAllocatedButIdle | pod's GPU under 5% for 30 min | info → owners, per namespace |

Runbooks: [docs/alerts.md](docs/alerts.md). Inhibitions: a broken GPU does not also trigger "idle GPU" for its owners, and the critical temperature alert replaces the warning.

## Run it

Needs Docker with Compose.

```bash
bash scripts/up.sh          # simulator, Prometheus, Alertmanager, alert sink, Grafana
bash scripts/inject.sh xid79   # break something (see the script for more)
bash scripts/test.sh        # the end-to-end checks below
bash scripts/down.sh
```

Grafana at http://localhost:3000 (dashboard "GPU fleet", read-only without login), Prometheus at :9090, Alertmanager at :9093. Everything binds to localhost.

```bash
docker compose run --rm --no-deps fleet-sim /usr/local/bin/fleetreport -prometheus http://prometheus:9090 -window 1h
```

## What the tests prove

| Layer | How | Checks |
|---|---|---|
| Go code | `go test -race` | simulator, control API, alert sink, Prometheus client, report |
| Rules | `promtool test rules` | 7 cases: each alert fires on time with the exact labels and annotations, and not before; XID 13 does not page; capacity counts a dead exporter |
| Config | `promtool check config`, `amtool check-config` | Prometheus and Alertmanager configs |
| Dashboard | generated by `tools/gen_dashboard.py` | CI fails if the JSON drifts; e2e runs every panel query |
| End to end | `scripts/test.sh` on Docker Compose | inventory numbers, XID 13 vs 79, quarantine routing, inhibition, team routing, exporter outage and capacity math, report content, Grafana provisioning, recovery with resolve notifications |
